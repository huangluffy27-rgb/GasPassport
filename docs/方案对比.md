# 三个候选方案

> **2026-11-21 方向变更**：本文三个方向仅作历史记录。经创意导师评估，Contend 的前提与 Monad 官方 FAQ（并行执行对开发者透明、冲突最多重执行一次）冲突，且与往届 ParallelScope 撞车，已转而做 **ChaosGas**（gas limit 统计体检），见 [README](../README.md)。

评估前提：Monad 是 EVM 等价的 L1，约 10k TPS 吞吐、~0.5s 出块、接近单槽最终性；共识与执行解耦（流水线 + 延迟执行），交易并行执行；gas 成本低。

因此真正的机会不是把以太坊应用原样搬过来，而是**只有在「高吞吐 + 亚秒确认 + 便宜」同时成立时才会出现的新场景**；反过来，新能力也会带来新问题，这同样值得做。

---

## 方案一：Contend —— 并行执行冲突诊断器

**类型**：开发者工具 / 基础设施

### 要解决的问题

Monad 的并行执行取决于多笔交易的存储访问集合是否冲突。但现实中大量合约沿用单线程写法：一个全局累加器、一张全量余额映射、一个热门金库合约。热点槽位（做市商、金库、热门 NFT 的 `balanceOf`）会让并行执行退化成「串行 + 反复重执行」，10k TPS 的实际落地值远低于宣传值。

更糟的是这个损失**对开发者不可见**：`forge test` 全绿，合约逻辑没错，只是并行度只有 1.2x，开发者既不知道该改哪一行，也没有指标能证明改完变好了。

### 方案

1. 运行测试或回放真实交易，采集每笔交易的存储读写集合（地址 + slot）；
2. 构建「交易 × 槽位」冲突图，计算并行度指标：理论加速比、冲突交易占比、Top N 热点槽；
3. 输出可执行的重构建议：余额按地址分桶分片、热门状态按用户拆合约、pull 式领取替代全局累加、批量合并写；
4. 把并行度接进 CI：低于阈值（如 3x）直接让流水线失败，让「并行友好」成为可回归的工程指标。

### 为什么必须做在 Monad 上

单线程执行链根本不存在「并行度」这个指标；只有并行 EVM 链需要它，而 Monad 是 EVM 等价、开发者基数最大的并行链。工具越早占位，越容易成为事实标准。

### 创新点

- 把「性能好不好」从玄学变成合约级的可测指标；
- 不止诊断，还给**改造建议 + 前后对照 benchmark**；
- 现有工具（Foundry trace、Tenderly、Phalcon）都只看单笔交易，不做跨交易的并行冲突建模。

### MVP 边界

- CLI：`contend analyze ./test` 输出 Markdown / HTML 报告；
- 3 个反例合约 + 3 个优化版合约做对照（朴素 ERC-20 / 分片余额 / pull 结算金库）；
- 一条 Monad testnet 部署脚本，实测优化前后的吞吐与并行度。

### 技术栈与验证指标

Foundry + TypeScript/Rust 解析 trace + React 报告页。
指标：同一负载下并行度 1.2x → 4x，热点槽冲突下降 80%。

### 风险

不同客户端 trace 格式存在差异；若做不到自动改写，退化为「诊断 + 建议」也成立。

## 方案二：StreamPay —— 按调用计费的流式微支付

**类型**：支付协议 / 应用

### 要解决的问题

API 与 AI Agent 的付费仍是订阅制或预充值：粒度粗、退款难、跨组织要人工对账。想改成「按调用付费」时，传统链上 gas 直接把模型打死——一笔 0.001 美元的服务付 0.5 美元 gas，经济上不成立。Monad 把单笔成本压到可忽略、确认压到亚秒，「按调用计费」第一次在链上成立。

### 方案

- 付款方开一条支付通道并存入额度；
- 每次调用离线签一张「累计消费凭据」，服务方立刻返回结果，不必等上链；
- 每 N 秒或达到额度阈值结算一次，链上只落最终累计额 + 收据，gas 摊薄到几乎为零；
- 收据是可验证的用量凭证，可用于分账（模型方 / 算力方 / 平台）、审计与信誉；
- 提供兼容 HTTP 402 的中间件，服务方一行接入。

### 为什么必须做在 Monad 上

亚秒最终性让「结算延迟」对用户无感；高 TPS 支持海量并行通道；低 gas 让计费粒度从「每月」变成「每次调用」。

### 创新点

- 从「订阅」变成「计量即结算」，不用的部分不需要预付；
- 通道 + 累计凭据把链上交互降到千分之一（相比 x402 式一次一付）；
- 收据变成可组合资产：自动分账 + 可审计用量 + 用信誉做服务方筛选。

### MVP 边界

- `PaymentChannel.sol`（存款 / 凭据结算 / 争议期 / 退款）；
- TypeScript SDK + Express 中间件；
- 一个真实 demo：给翻译或摘要 API 按 token 计费，页面实时显示消耗、未结算余额、收据列表。

### 技术栈与验证指标

Solidity + Foundry；TypeScript SDK；Vite + React dashboard。
指标：单次调用链上成本趋近于 0，结算延迟 < 2s，通道资金利用率可查。

### 风险

需要同时防「服务方收钱不干活」与「付款方双花凭据」；争议期参数要在体验与安全间取舍。

## 方案三：FairBatch —— 亚秒批量拍卖与订单流回收

**类型**：交易基础设施

### 要解决的问题

新链早期流动性薄：公开 mempool + 先到先得排序，让三明治攻击的收益远高于做 LP 的收益，LP 被劝退；MEV 收益流向少数搜索者，生态本身拿不到。以太坊上的批量拍卖受 12 秒出块限制，用户要等十几秒才成交，体验不可接受——所以「公平排序」一直停留在小圈子方案里。

### 方案

- 用户提交**加密订单**（MVP 用短窗 commit-reveal，进阶用阈值加密）；
- 每 1–2 个区块（0.5–1 秒）撮合一批，统一清算价成交；
- solver 竞争提交清算方案，价差按规则分给 LP / 协议 / 用户；
- 未成交订单原样退回，不产生额外成本。

### 为什么必须做在 Monad 上

0.5s 出块把「批量等待」从 12s 压到 1s 级，这是批量拍卖体验第一次能接近 CEX 的执行环境；低 gas 支持高频小额订单进入同一批次。

### 创新点

- 公平排序不依赖私有 mempool 或中心化 relay，而是由出块速度直接支撑的**开放批量拍卖**；
- solver 竞争 + 收益回流 LP，把 MEV 从负外部性变成流动性激励；
- 批内统一价天然消除同批三明治，规则可验证、可审计。

### MVP 边界

- `BatchAuction.sol`（commit-reveal 版）+ keeper 撮合脚本；
- 单个交易对（MON / 测试 USDC）demo，展示「同批统一价、无三明治」；
- 指标：批内价差、LP 收益、订单从提交到成交的延迟。

### 技术栈与验证指标

Solidity + Foundry + TypeScript keeper；前端展示批次与清算价。

### 风险

冷启动流动性是最大变量；solver 生态需要激励设计；阈值加密依赖额外基础设施（MVP 先不做）。

## 对比

| 维度 | Contend | StreamPay | FairBatch |
|---|---|---|---|
| 问题真伪 | 高（并行链独有） | 高（AI 付费刚需） | 中高（依赖流动性） |
| Monad 依赖度 | 强（无并行则无意义） | 强（低成本高频） | 强（亚秒批量） |
| 创新强度 | 高 | 中高 | 高 |
| MVP 难度 | 中 | 低 | 高 |
| 可演示性 | 中（数据 + 图表） | 高（真实 API 计费） | 高（可视化撮合） |
| 冷启动风险 | 低（B 端工具） | 中（需双边接入） | 高（需流动性） |

## 建议

- 想突出**技术深度 + 可量化结果**：选 Contend（最容易做出「优化前后 4 倍差异」的硬数据）
- 想做出**完整产品闭环 + 好演示**：选 StreamPay（用户、SDK、Dashboard 都能跑通）
- 想讲**最强的叙事**但接受最大工程量：选 FairBatch
